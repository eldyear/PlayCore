# CLUB_SYSTEM_SPEC.md — Система управления компьютерным клубом (аналог Senet)

Документ для ИИ-агента (OpenCode + DeepSeek V4 Pro, Linux).
Состоит из двух частей:

- **Часть A — мастер-промпт** (как работать, правила, формат отчётов).
- **Часть B — архитектура и логика** (что строить, до уровня таблиц, протокола и состояний).

Как запускать: положите этот файл в корень пустого репозитория, создайте рядом `AGENTS.md` (текст в конце документа, раздел 20) и дайте агенту первую команду:

> Прочитай CLUB_SYSTEM_SPEC.md целиком. Создай PROGRESS.md и выполни Этап 0. После этапа остановись и отчитайся по формату из раздела A.5.

Дальше по одному этапу за раз (раздел 17). Не давайте агенту «сделай всё сразу»: качество упадёт.

# ЧАСТЬ A. МАСТЕР-ПРОМПТ

## A.1 Роль и цель

Ты — старший инженер, который строит с нуля продукт: **облачную систему управления физическим компьютерным (игровым) клубом**. Продукт состоит из:

1. **Сервера** (API + WebSocket-шлюз + биллинг + база данных).
2. **Веб-панели администратора/владельца**.
3. **Клиентской программы для Windows 11**, которая стоит на каждом игровом ПК: блокирует ПК, считает время, показывает баланс и игры, выполняет команды сервера.
4. **Веб-приложения игрока (PWA)**: баланс, бронирование, вход по QR.

Функциональный ориентир — Senet и подобные системы (SmartShell, Gizmo, ggLeap): интерактивная карта зала, клубные аккаунты, тарифы и пакеты часов, касса и бар, смены, отчёты, лояльность, бронирование, роли персонала, мониторинг ПК.

**Критическое нефункциональное требование:** клиентская программа обязана быть **полностью совместимой с FACEIT Anti-Cheat** и не вызывать блокировок: ничего не лезть в процессы игр, не ставить драйверы, не ломать цепочку доверия загрузки. Подробные правила — раздел B.2. Нарушение этих правил считается критическим дефектом.

Юридически и этически: проект — легитимный софт для клуба. **Запрещено** добавлять любые механизмы, скрывающие программу от античита, обходящие его проверки или маскирующие процессы. Совместимость достигается тем, что программа ничего «подозрительного» не делает, а не маскировкой.

## A.2 Жёсткие правила работы

1. **Работай этапами** (раздел B.17). Не переходи к следующему этапу, пока не выполнены критерии приёмки текущего.
2. **Сначала читай, потом пиши.** Перед каждым этапом перечитай релевантные разделы этого файла. Не угадывай: если в спецификации есть ответ, следуй ему.
3. **Не задавай вопросов без необходимости.** Если не хватает детали, прими разумное решение, запиши его в `DECISIONS.md` (дата, контекст, решение, причина) и иди дальше. Спрашивай только если решение необратимо или меняет архитектуру.
4. **Никаких заглушек и «TODO позже» в критичном коде.** Биллинг, учёт денег, авторизация, протокол, защита клиента делаются полностью и с тестами. Допустимы адаптеры-заглушки только для внешних интеграций (фискальный регистратор, платёжные шлюзы) — за чётким интерфейсом.
5. **Тесты обязательны.** Нет теста — нет «готово». Тесты запускай сам и показывай результат. Не правь тесты, чтобы они прошли: правь код.
6. **Деньги — только целые числа** в минорных единицах (bigint). Никаких float/double для денег и времени биллинга.
7. **Сервер — источник истины** для времени, денег и состояния сессий. Клиент ничего не решает сам, только исполняет и показывает.
8. **Безопасность по умолчанию:** параметризованные запросы, валидация всех входов, rate limit, аудит денежных операций, секреты только из окружения, никаких паролей в репозитории.
9. **Ограничение среды:** ты работаешь на Linux и **не можешь запустить Windows-клиент**. Поэтому архитектура клиента специально разделена (раздел B.8): вся логика — в переносимой библиотеке с юнит-тестами на Linux, Windows-специфичный код — тонкий слой. Для Windows-части пиши **ручной тест-план** (`docs/windows-manual-test-plan.md`), а в отчёте честно помечай, что на Windows не проверено.
10. **Не выдумывай API Windows.** Если не уверен в сигнатуре или поведении, читай документацию Microsoft (если есть доступ) или пометь место `// VERIFY-ON-WINDOWS:` и внеси в тест-план.
11. **Не добавляй лишних зависимостей.** Каждую новую библиотеку обоснуй в `DECISIONS.md` (лицензия, поддержка, зачем). Закрепляй версии.
12. **Коммиты:** маленькие, осмысленные, формат `type(scope): message` (feat, fix, test, docs, chore). После каждого завершённого шага коммит.
13. **Язык:** код, идентификаторы, комментарии к коду — на английском. Интерфейс продукта — на русском, с готовностью к i18n (все строки в словарях, не в коде).

## A.3 Порядок работы внутри этапа

1. Прочитай этап в B.17, составь план в `PROGRESS.md` (чек-лист).
2. Реализуй по пунктам: миграции → доменная логика → API → тесты.
3. Запусти `make lint test` (раздел B.16). Исправь всё.
4. Обнови `PROGRESS.md`, `DECISIONS.md`, документацию.
5. Сделай отчёт (A.5).

## A.4 Чего делать категорически нельзя

- Писать код, который читает или пишет память чужих процессов, внедряет DLL, ставит хуки в игры или лаунчеры, использует драйверы режима ядра.
- Использовать библиотеки мониторинга железа, которые загружают собственный драйвер ядра (см. B.2).
- Отключать или предлагать отключать Secure Boot, TPM, VBS/HVCI, IOMMU, включать режим тестовой подписи драйверов.
- Хардкодить секреты, ключи подписи, пароли.
- Считать деньги или время на клиенте как источник истины.
- Менять спецификацию молча: любое отступление записывай в `DECISIONS.md`.

# ЧАСТЬ B. АРХИТЕКТУРА И ЛОГИКА

## B.1 Границы и цели

**MVP (этапы 0–4):** учёт клиентов и баланса, тарифы, сессии и биллинг, клиентская программа, панель администратора с картой зала, смены и касса (базово).

**Версия 1.0 (этапы 5–7):** бар и склад, отчёты, лояльность и промокоды, бронирование, приложение игрока, автообновление клиента, укрепление безопасности.

**Вне объёма (не делать, пока не попросят):** майнинг, токены, криптовалюты, подключение консолей, удалённый экран (screen sharing), телевизионные контроллеры, онлайн-платежи (оставить интерфейс-заглушку).

**Масштаб:** до 200 ПК на клуб, до 20 клубов на один сервер, одновременно до 4000 WebSocket-соединений. Рассчитывай на один VPS (4 vCPU / 8 ГБ).

**Валюта** задаётся в настройках клуба (ISO 4217), хранится как целое число минорных единиц, 2 знака. В сидах по умолчанию `USD`.

## B.2 Совместимость с FACEIT Anti-Cheat (обязательные правила)

### Что известно о требованиях FACEIT

Требования к игроку, поэтому и к игровым ПК клуба (подтверждено на support.faceit.com и в новостях за 2025–2026):

- **Windows 11** (64-bit); с 14 октября 2026 Windows 10 не поддерживается.
- **TPM 2.0** и **Secure Boot** включены (обязательны с 25 ноября 2025).
- **IOMMU** и **VBS** (виртуализационная защита) включены, раскатываются волнами.
- Античит проверяет целостность цепочки загрузки и памяти системы через аттестацию TPM; нельзя, чтобы в систему были загружены неподписанные или модифицированные драйверы.

> Требования FACEIT меняются. Перед релизом и раз в квартал агент (или человек) обязан сверяться с актуальной страницей support.faceit.com по anti-cheat requirements и обновлять этот раздел.

### Принципы дизайна клиента (MUST NOT)

1. **Никаких драйверов режима ядра**, своих и сторонних. Клиент целиком в user-mode: Windows Service + пользовательское приложение.
2. **Никаких библиотек, которые подгружают kernel-драйвер**, включая популярные библиотеки аппаратного мониторинга (LibreHardwareMonitor, OpenHardwareMonitor, HWiNFO-SDK и т.п. — они используют драйвер доступа к портам/MSR). Температуры и нагрузку берём только штатными user-mode средствами: счётчики производительности (PDH), WMI, для NVIDIA — NVML, для AMD — ADL/ADLX. Если источника нет — метрику не показываем.
3. **Никакой инъекции в процессы игр и лаунчеров:** нет DLL-инъекции, нет хуков DirectX/Vulkan/OpenGL, нет хуков API чужих процессов.
4. **Никакого чтения и записи памяти чужих процессов.** При работе с процессами запрашивай минимум прав: `PROCESS_QUERY_LIMITED_INFORMATION` и `PROCESS_TERMINATE` (последний — только для завершения процессов пользовательской сессии по окончании сессии). Запрещены `PROCESS_VM_READ`, `PROCESS_VM_WRITE`, `PROCESS_VM_OPERATION`, `PROCESS_ALL_ACCESS`, а также привилегия `SeDebugPrivilege`.
5. **Оверлей клиента — отдельное окно** (topmost, прозрачное для кликов где нужно), а не рисование поверх игры через хук. Ограничение «в эксклюзивном полноэкранном режиме окно может быть не видно» принимаем; показываем уведомления через системные toast-уведомления Windows и через окно при выходе из игры.
6. **Глобальные клавиатурные хуки (`WH_KEYBOARD_LL`) — только на экране блокировки** и снимаются на время активной сессии. Ограничение клавиш в сессии делаем политиками Windows (реестр, Group Policy), а не хуками.
7. **Не трогаем защиту платформы:** клиент не отключает и не изменяет Secure Boot, TPM, VBS/HVCI, IOMMU, Defender, не включает test signing, не требует отключения Core Isolation.
8. **Весь исполняемый код подписан** действительным сертификатом подписи кода (Authenticode). Неподписанные бинарники в продакшене запрещены.
9. **Никаких «скрытых» процессов:** понятные имена, понятные описания в свойствах файла, штатная служба Windows, штатная запись в «Программы и компоненты».
10. **Не используем решения «заморозки диска»** (Deep Freeze, Shadow Defender и подобные драйверные продукты): они ставят собственные драйверы. Очистку делаем сами в user-mode (B.8.7).
11. **Удалённое управление:** никаких встроенных средств удалённого рабочего стола и захвата экрана в MVP. Сторонние средства удалённого доступа (AnyDesk, TeamViewer и т.п.) на игровых ПК не ставим без отдельного теста совместимости.
12. **Никакого перехвата или подмены ввода** (макросы, эмуляция клавиш/мыши) вне собственных окон клиента.

### Принципы дизайна клиента (MUST)

1. **Проверка готовности ПК к FACEIT** (`ComplianceChecker`): при старте и раз в час клиент собирает и отправляет серверу отчёт:
   - версия и сборка Windows (нужна Windows 11, 23H2 или новее);
   - TPM 2.0: наличие, включён, готов (WMI `root\CIMV2\Security\MicrosoftTpm` → `Win32_Tpm`);
   - Secure Boot включён (реестр `HKLM\SYSTEM\CurrentControlSet\Control\SecureBoot\State`, значение `UEFISecureBootEnabled`);
   - VBS: статус работы (WMI `root\Microsoft\Windows\DeviceGuard` → `Win32_DeviceGuard`: `VirtualizationBasedSecurityStatus`, `SecurityServicesRunning`);
   - защита DMA/IOMMU (`Win32_DeviceGuard.AvailableSecurityProperties`, значение защиты DMA);
   - режим тестовой подписи (должен быть выключен);
   - наличие неподписанных драйверов (информативно).
   Любой пункт, который не удалось прочитать, помечается `unknown`, а не `ok`. Все пути чтения пометить `// VERIFY-ON-WINDOWS:`.
2. **Панель «FACEIT-ready»** в админке: зелёный/жёлтый/красный индикатор по каждому ПК, причина красного. Это главный инструмент владельца, чтобы не ловить блокировки на проде.
3. **Инсталлятор** при установке проверяет отчёт готовности и честно предупреждает, что нужно исправить в BIOS/Windows (без автоматического изменения защитных настроек).
4. **Тест-план совместимости** (`docs/faceit-compat-test-plan.md`), который выполняется человеком на реальном железе после каждого релиза клиента:
   - чистая Windows 11 с Secure Boot, TPM, VBS, IOMMU → установка клиента → установка FACEIT AC → запуск матча CS2 → клиент работает в фоне, блокировки нет;
   - смена сессии без перезагрузки: вход, игра, завершение, повторный вход;
   - обновление клиента между сессиями;
   - список «известных конфликтов» (заполняется по факту).
5. **Лаунчер FACEIT и клиент FACEIT AC ставит и обновляет клуб штатными средствами**, наша программа их не модифицирует, плитка в оболочке просто запускает их.

### Что нельзя обещать

Гарантировать, что FACEIT никогда не заблокирует, нельзя: решение принимает их античит и политика платформы. Поэтому:

- строго соблюдаем правила выше;
- ведём панель FACEIT-ready;
- при подозрении на конфликт собираем диагностический пакет клиента (версии, список драйверов и служб без персональных данных) для обращения в поддержку FACEIT;
- отдельно владельцу клуба стоит уточнить у FACEIT, как их правила относятся к общим клубным ПК (несколько аккаунтов с одного устройства). Это вопрос политики платформы, программой он не решается.

## B.4 Технологический стек (зафиксирован)

| Часть | Выбор | Причина |
|---|---|---|
| Сервер | **Go 1.23**, `chi`, `pgx`, `sqlc`, `golang-migrate`, `coder/websocket`, `zerolog` | один бинарник, отличная конкурентность, просто собирать на Linux |
| БД | **PostgreSQL 16** (расширение `btree_gist` для бронирования) | транзакции, ограничения, диапазоны времени |
| Веб-панель | **React 18 + Vite + TypeScript + Tailwind**, TanStack Query, Zustand | быстрая разработка, тесты на Linux |
| Приложение игрока | **PWA** из того же веб-проекта (отдельный маршрут `/p`) | не нужны сторы |
| Клиент ПК | **C# / .NET 8**, Windows Service + **WPF** оболочка с **WebView2** | UI на HTML тестируется в браузере на Linux, системная часть — тонкая |
| Протокол клиента | JSON поверх **WebSocket (TLS)**, версионированный | просто отлаживать |
| Установщик | **NSIS** (собирается на Linux через `makensis`) | Windows-машина не нужна для сборки |
| Подпись кода | `osslsigncode` на Linux, ключ из секрета CI | сборка без Windows |
| Обновления | подписанный манифест **Ed25519** | проверка целостности |
| Пароли | **argon2id** | стандарт |
| Токены персонала | короткие JWT (15 мин) + refresh (httpOnly cookie, ротация) | безопасность и удобство |
| Деплой | Docker Compose + Caddy (автоматический TLS) | просто и воспроизводимо |
| Тесты | Go: `testing` + `testcontainers`; TS: Vitest + Playwright; .NET: xUnit | покрытие всех слоёв |

Сборка Windows-клиента на Linux: в `.csproj` включить `<EnableWindowsTargeting>true</EnableWindowsTargeting>`, публиковать `dotnet publish -r win-x64 --self-contained false`. Запускать WPF на Linux нельзя, поэтому тестируются только переносимые библиотеки.

## B.7 Биллинг и логика сессий

Файл `docs/billing.md` должен дублировать этот раздел.

### B.7.1 Принципы

- Источник времени — **сервер**. Клиент показывает остаток по `ends_at_estimate` и локальному монотонному таймеру.
- Списания происходят **тиками раз в 60 секунд** на сервере (воркер на каждую активную сессию). Тик идемпотентен: `(session_id, tick_no)` уникален. Повторный запуск воркера не создаёт двойного списания.
- Стоимость за интервал вычисляется как `round_half_up(price_per_hour * seconds / 3600)` по сегментам тарифа; разница с уже списанным дописывается в ledger. Сумма за сессию всегда совпадает с формулой, что проверяется property-тестом.
- Любое изменение баланса — через пакет `wallet` в одной транзакции (`SELECT … FOR UPDATE` игрока).

### B.7.2 Выбор цены

Для момента `t` в зоне `z` у игрока из групп `G`:

1. Берём активные тарифы, подходящие по `zone_ids` и `player_group_ids` (пустой список = «все»).
2. Из них — с наибольшим `priority`.
3. В тарифе ищем правило, где `t` попадает в `days_of_week` и окно времени (окна через полночь: `time_from > time_to`).
4. Если несколько правил подходят — берём с меньшей длиной окна (специфичнее), при равенстве — меньшую цену.
5. Если ничего не подошло — ошибка конфигурации: сессию не стартуем, администратору показываем понятную причину.

На границе окон (например, переход с дневного на ночной) сессия делится на **сегменты** с разными ценами; сегменты считаются отдельно. Скидка ранга/группы применяется к цене часа до округления: `price * (100 - discount) / 100`, берётся максимальная из применимых скидок (не суммируются).

### B.7.3 Пакеты часов

- Покупка пакета: списание денег (`package_purchase`) + запись `player_packages`.
- При старте сессии, если у игрока есть подходящий пакет (зона и окно времени), сначала расходуется он: тик уменьшает `seconds_left` на 60, денег не списывается.
- Когда пакет исчерпан или вышел за допустимое окно, сессия **автоматически переходит на почасовой тариф** (настройка клуба `package_fallback = hourly | stop`).
- Просроченные пакеты сгорают по `expires_at` (джоб раз в час).

### B.7.4 Конечный автомат сессии

```
CREATED ──(client ack)──► ACTIVE ──(low funds)──► ENDING (grace) ──► ENDED
   │                        │  ▲                      │
   │                        │  └──(пополнение)────────┘ возврат в ACTIVE
   └──(timeout 30s)► FAILED │
                            └──(admin/player stop)──► ENDED
```

- **Старт:** проверка `balance >= min_charge` (и > 0), ПК в состоянии `LOCKED`, нет другой активной сессии у игрока (политика `one_session_per_player`, по умолчанию да). Транзакция: создать сессию `CREATED`, послать клиенту `session.start`. Если ack не пришёл за 30 с — `FAILED`, ПК остаётся заблокированным, денег не списано.
- **Низкий баланс:** за 5 минут до исчерпания (по текущей цене) — предупреждение клиенту (`session.warn`), за 1 минуту — второе. Игрок может пополнить баланс у администратора или в приложении; сессия продолжается без перерыва.
- **Исчерпание:** состояние `ENDING` на `grace_seconds` (по умолчанию 60); затем `ENDED` с причиной `time_out`, клиенту `session.end`.
- **Завершение игроком:** кнопка в оболочке → `session.stop.request` → сервер финализирует (дописывает последний неполный тик пропорционально) → `session.end`.
- **Завершение администратором:** сразу, с записью в аудит. Возврат средств — отдельной операцией `refund`.
- **Перенос на другой ПК:** одна транзакция: закрыть сессию на ПК A, создать на ПК B с тем же `tariff_snapshot`, с учётом цены зоны B (доплата или без — настройка).
- **Гостевая сессия:** без игрока; администратор принимает наличные, сумма `guest_prepaid`; время рассчитывается как `prepaid / price`; по окончании — `ENDING`/`ENDED`.

### B.7.5 Потеря связи

- Клиент получает от сервера **подписанный билет сессии** (`session.ticket`): `{session_id, pc_id, device_id, ends_at_estimate, issued_at, nonce}` + подпись Ed25519 ключом сервера (публичный ключ вшит в клиент).
- Если связь потеряна, клиент **продолжает сессию** до `ends_at_estimate`, но не дольше `offline_grace_minutes` (по умолчанию 15) от последнего ответа сервера, считая по монотонному таймеру (`Stopwatch`), а не по системным часам.
- По истечении — блокировка с сообщением «нет связи с сервером, обратитесь к администратору».
- При восстановлении связи клиент шлёт `session.sync {seconds_elapsed_offline}`; сервер пересчитывает по своим данным (источник истины — сервер), досписывает недостающее; **если баланс ушёл бы в минус — просто закрываем сессию и фиксируем убыток в `pc_events`**, баланс не уходит ниже нуля.
- Если сервер недоступен более N минут при запуске ПК: экран блокировки с индикатором «нет связи», только администратор может разрешить аварийный режим локальным мастер-паролем (хранится как argon2id-хеш в защищённой конфигурации).

### B.7.6 Пополнение, возвраты, коррекции

- Пополнение наличными/картой: операция кассира внутри открытой смены (`topup` + `payments`).
- Возврат: только менеджер/владелец; запись `refund` со ссылкой на исходную; аудит.
- Коррекция баланса: `adjustment` с обязательным комментарием; роль не ниже менеджера.
- Бонусы: начисляются и тратятся отдельным полем `bonus_amount`; бонусами можно оплатить не более `bonus_max_percent` стоимости (по умолчанию 50%).

### B.7.7 Обязательные тесты биллинга

1. Property-тест: для случайных тарифов, окон, расписаний и длительностей сумма списаний по тикам равна эталонной формуле ±0 минорных единиц.
2. Идемпотентность тика (двойной запуск воркера).
3. Конкурентность: 50 параллельных списаний с одного баланса не уводят в минус.
4. Переход через полночь и смена цены на границе окна; смена летнего времени на уровне таймзоны клуба.
5. Пакет → fallback на почасовой.
6. Потеря связи, `session.sync`, закрытие при нехватке денег.
7. Перенос на другой ПК.
8. Попытка старта двух сессий на одном ПК (должен сработать частичный уникальный индекс).

### B.8.2 Установка и первый запуск

1. Установщик NSIS (запуск от администратора): копирует файлы в `%ProgramFiles%\ClubAgent`, регистрирует службу `ClubAgent` (автозапуск, восстановление при сбое: перезапуск через 5/15/60 с), создаёт локальную стандартную учётную запись `ClubPlayer` (без прав администратора, пароль случайный, хранится в DPAPI machine scope), настраивает автовход этой записи, прописывает запуск `ClubShell.App` для неё.
2. Раздел реестра/ACL `%ProgramData%\ClubAgent`: запись только `SYSTEM` и `Administrators`, чтение игроку запрещено (конфиг, секрет устройства, логи).
3. **Enrollment:** администратор в панели жмёт «Добавить ПК» → одноразовый токен (TTL 24 ч) → вводится при установке или передаётся параметром. Клиент вызывает `POST /api/v1/devices/enroll {token, hw_fingerprint, hostname, client_version}`, получает `device_id` + `device_secret`; секрет шифруется DPAPI (machine scope) и кладётся в `%ProgramData%\ClubAgent`.
4. `hw_fingerprint` — хеш из стабильных идентификаторов (UUID материнской платы через WMI, серийник диска); отпечаток нужен для привязки устройства и антиклонирования образа, но не используется для слежки за пользователем. В панели при клонировании образа — предупреждение «два устройства с одним отпечатком».
5. Установщик запускает `ComplianceChecker` и выводит отчёт (B.2); ничего в защитных настройках сам не меняет.

### B.8.3 Состояния ПК (конечный автомат `Club.Core`)

```
BOOT → CONNECTING → LOCKED ⇄ STARTING → IN_SESSION → ENDING → CLEANUP → LOCKED
                       │                    │
                       └─ MAINTENANCE (админ)└─ OFFLINE_GRACE → LOCKED(offline)
RESERVED — отображение поверх LOCKED за N минут до брони
```

Переходы — только по событиям (`ServerCommand`, `LocalEvent`, `TimerEvent`), каждое событие журналируется; неверный переход игнорируется и пишется в `pc_events`.

### B.8.4 Экран блокировки и оболочка

- `LOCKED`: полноэкранное окно на всех мониторах (`WS_EX_TOPMOST`, перекрывает рабочий стол, перехватывает фокус); показывает номер места, зону, логотип клуба, QR-код входа, поле логина/PIN, кнопку «Позвать администратора», статус связи, при брони — «Забронировано до HH:MM».
- Окно блокировки — **обычное окно приложения** ClubShell, не драйверный перехват. Глобальный хук клавиатуры (Alt+Tab, Win, Ctrl+Esc) — **только пока окно блокировки на экране**, и снимается при начале сессии (B.2).
- Ограничения в сессии — **политиками** для учётной записи `ClubPlayer`: запрет Диспетчера задач, смены пароля, `regedit`, `cmd`/PowerShell (кроме белого списка), панели управления, смены учётных записей, установки программ и запуска из `%TEMP%` вне белого списка (AppLocker/SRP по возможности). Политики применяются `IPolicyManager` и описаны декларативным файлом `policies.json`.
- `IN_SESSION`: рабочий стол клуба (плитки игр и программ из каталога), боковая панель (остаток времени и денег, тариф, ранг и бонусы, вызов администратора, заказ из бара, чат, кнопка «Завершить сессию»). Панель — **отдельное окно** с `WS_EX_NOACTIVATE`, не отбирающее фокус у игры; автоскрытие.
- Предупреждения о конце времени: toast Windows + звук; при исчерпании — окно поверх всего после выхода из игры/через 60 с grace.

### B.8.5 Каталог игр и программ

- Серверный каталог (`apps`: название, иконка, категория, команда запуска: `exe`, `uri` или `launcher`, видимость по зонам).
- Автоопределение установленных игр Steam (чтение `libraryfolders.vdf` и `appmanifest_*.acf`), Epic (манифесты), Battle.net и Riot: только **чтение файлов конфигурации** лаунчеров, без вмешательства в их процессы. Запуск через штатные URI (`steam://rungameid/…`) или исполняемый файл лаунчера.
- Плитки «FACEIT» и «Counter-Strike 2» просто запускают установленное клубом ПО.
- Клуб сам ставит и обновляет игры штатными средствами; наша программа **не распространяет и не модифицирует** чужие игры и лаунчеры.

### B.8.6 Связь с сервером

- WebSocket `wss://…/ws/device`, заголовок `Authorization: Bearer <device_token>`, где токен — короткоживущий (10 минут) JWT, получаемый по `POST /api/v1/devices/token` с HMAC-подписью `device_secret` (защита от повторного воспроизведения: `nonce` + `ts`, допуск ±60 с).
- `heartbeat` каждые 5 с (сервер считает ПК недоступным после 20 с тишины → статус `OFFLINE`).
- Переподключение: экспоненциальная задержка 1→2→4→…→30 с с jitter ±20%; во время реконнекта экран и сессия работают по офлайн-правилам (B.7.5).
- Все сообщения: конверт `{v, id, type, ts, payload}`, подтверждение критичных команд (`ack` с `id`), повтор неподтверждённых; идемпотентность по `id`.
- Версия протокола проверяется при `hello`; несовместимая — клиент показывает «требуется обновление» и не стартует сессии.

### B.8.7 Завершение сессии и очистка (`CLEANUP`)

После `session.end`:

1. Показать экран блокировки немедленно (скрыть игровые окна).
2. Завершить пользовательские процессы **только** в сессии `ClubPlayer`: корректно (`CloseMainWindow`), затем через 10 с принудительно (`TerminateProcess`). Список исключений (процессы клуба, AC-службы, сервис ClubAgent) защищён `protected_processes`. Системные процессы и сторонние службы не трогаем.
3. Очистка по конфигурируемому списку: загрузки, рабочий стол, документы, `%TEMP%`, профили браузеров, кеши и токены входа лаунчеров (Steam, Epic, Battle.net, Riot, FACEIT, Discord) через **штатный выход** либо удаление известных файлов локальных токенов. Пути для каждого приложения вынести в `cleanup.json` и пометить `// VERIFY-ON-WINDOWS:`; не очищать каталоги игр.
4. По желанию клуба (`cleanup.logoff_profile=true`) — полный выход из `ClubPlayer`, удаление профиля через `DeleteProfile` и повторный автовход.
5. Отправить серверу `cleanup.done` с длительностью и ошибками; ПК переходит в `LOCKED`.

Очистка идемпотентна, переживает падение службы (маркер незавершённой очистки на диске, при старте службы выполняется повторно).

### B.8.8 Мониторинг ПК

Каждые 30 секунд: нагрузка CPU/RAM (PDH), температура и нагрузка GPU (**только NVML/ADLX, без драйверных библиотек**), свободное место, состояние сети, время работы системы. Метрика недоступна → поле `null`. Данные идут в панель (цвет карточки ПК при перегреве). Персональные данные игрока не собираются; список запущенных процессов не отправляется (только по явному запросу администратора диагностики и только имена/версии клубного ПО).

### B.8.9 Обновления клиента

- Сервер отдаёт `update.available {version, url, sha256, signature}`; манифест подписан Ed25519, публичный ключ вшит в клиент.
- Обновление **только** в состоянии `LOCKED`, никогда не во время сессии.
- Скачивание в `%ProgramData%\ClubAgent\staging`, проверка sha256 и подписи, а также Authenticode-подписи файлов; затем подмена файлов остановленной службой через вспомогательный `ClubUpdater.exe` (подписанный, также user-mode). При ошибке — откат к предыдущей версии; успешный запуск подтверждается `health.ok` в течение 60 с, иначе откат автоматически.
- Постепенная раскатка: `rollout_percent`, канал `stable`/`beta`, ручной откат в панели.

### B.8.10 Журналы и диагностика

Логи в `%ProgramData%\ClubAgent\logs` (ротация 14 дней, JSON-строки, без персональных данных и без секретов). Команда «Диагностический пакет» в панели: версия клиента/ОС, отчёт compliance, список служб и драйверов (имена и версии), хвост логов. Пакет формируется по запросу администратора и скачивается из панели.

## B.9 Протокол клиент ↔ сервер (`docs/protocol.md`)

Конверт: `{"v":1,"id":"uuid","type":"…","ts":"RFC3339","payload":{…}}`. Критичные сообщения требуют `ack {ref_id}`.

Правила: неизвестные поля игнорируются; неизвестный `type` логируется и игнорируется; несовместимая `proto_version` → `hello.reject`. Размер сообщения ≤ 64 КБ. Лимит на клиент: 20 сообщений/с (иначе закрытие соединения).

### REST API (`/api/v1`, схема OpenAPI в `docs/api.md`)

Группы: `auth` (вход персонала, refresh, выход) · `clubs` · `zones` · `pcs` (+`/pcs/{id}/command`) · `devices/enroll`, `devices/token` · `players` (+поиск, пополнение, блокировка, история) · `sessions` (старт/стоп/перенос/продление) · `tariffs`, `packages` · `wallet` (операции) · `products`, `stock`, `orders` · `shifts`, `cash` · `reservations` · `promos`, `loyalty` · `reports` · `releases` · `compliance` · `audit` · `player-app/*` (авторизация игрока, баланс, брони, QR-подтверждение входа).

Единый формат ошибок: `{"error":{"code":"insufficient_funds","message":"…","details":{…}}}`. Все списки с пагинацией (`limit`, `cursor`). Все изменяющие запросы поддерживают заголовок `Idempotency-Key`.

## B.10 Безопасность (`docs/security.md`)

- **Транспорт:** только TLS; HSTS; WebSocket только по `wss`.
- **Персонал:** argon2id, блокировка после 5 неудачных входов (экспоненциальная пауза), обязательная смена пароля владельца при первом входе, опциональный TOTP для ролей `owner`/`manager`. JWT 15 мин + refresh с ротацией; список отозванных refresh.
- **RBAC:** матрица прав в `internal/rbac` (код, тесты). Минимально: `cashier` — пополнения и продажи в своей смене, без возвратов; `admin` — сессии, ПК, игроки; `manager` — возвраты, коррекции, тарифы, отчёты; `owner` — всё, включая персонал и релизы; `tech` — ПК, обновления, compliance, без доступа к деньгам.
- **Устройства:** `device_secret` хранится только хешем (argon2id/HMAC) на сервере; отзыв устройства мгновенно закрывает WebSocket; токен-обмен с защитой от повтора.
- **Игроки:** PIN ≥ 4 цифр + ограничение попыток (5 за 10 минут на ник/IP/ПК); при желании пароль и телефон; QR-коды одноразовые, TTL 60 с.
- **Rate limit** на публичные и аутентификационные эндпоинты; защита от перебора никнеймов (одинаковые ответы).
- **Аудит:** любая денежная операция, смена роли/тарифа, ручной старт/стоп, коррекция, возврат, отзыв устройства — запись в `audit_log` (append-only).
- **Данные:** персональные данные игроков минимальны; экспорт и удаление по запросу игрока; бэкапы БД шифруются; логи без PIN, паролей, токенов.
- **Секреты и ключи:** из окружения или секрет-хранилища; ключ подписи релизов и ключ подписи билетов — отдельные, ротируемые (`ticket_pubkey_id`).
- **Веб:** CSP, `SameSite`/`httpOnly` cookies, защита от CSRF для cookie-эндпоинтов, санитизация вывода, проверка размеров загрузок.
- **Зависимости:** автоматическая проверка уязвимостей в CI (`govulncheck`, `npm audit`, `dotnet list package --vulnerable`).

## B.11 Веб-панель администратора

Страницы (русский интерфейс, адаптив под планшет администратора, тёмная тема по умолчанию):

1. **Карта зала** (главная): схема клуба с ПК, цвета по статусу (свободен, в сессии, забронирован, офлайн, обслуживание, перегрев, не FACEIT-ready). Клик по ПК: игрок, остаток, тариф, кнопки (старт сессии, стоп, перенос, сообщение, перезагрузка, выключение, блокировка, диагностика). Редактор схемы (drag-and-drop, координаты в `pcs.layout`).
2. **Сессии:** активные и история; фильтры; экспорт CSV.
3. **Игроки:** поиск (ник/телефон), карточка (баланс, бонусы, ранг, история, пакеты, блокировка, заметка), быстрое пополнение.
4. **Касса и смены:** открытие/закрытие смены, наличные, инкассация, расходы, сверка (ожидаемо/факт), печать итогового отчёта.
5. **Бар и склад:** товары, заказы с ПК (всплывающее уведомление), приход, списание, остатки, минимальные остатки с оповещением.
6. **Тарифы и пакеты:** редактор правил с превью цены на выбранный день/час; проверка пересечений.
7. **Лояльность и промо:** ранги, кешбэк, промокоды, акции (happy hour — правилом тарифа).
8. **Бронирования:** календарь по ПК/зонам.
9. **Отчёты:** выручка по дням/сменам/сотрудникам/методам оплаты, загрузка ПК по часам (heatmap), топ игроков, продажи бара, движение склада; экспорт CSV/XLSX.
10. **ПК и устройства:** добавление ПК (токен установки), версии клиента, FACEIT-ready отчёты, диагностический пакет, отзыв устройства.
11. **Каталог игр и программ**, настройки клуба, персонал и роли, журнал аудита, релизы клиента.

Данные карты зала обновляются по SSE/WebSocket (`/api/v1/stream`), без опроса. Каждое действие с деньгами требует подтверждения и показывает итог до применения.

## B.12 Лояльность и промокоды

- Кешбэк бонусами `cashback_percent` от оплаченных сессий и покупок; ранг пересчитывается по `lifetime_spent` (джоб + при каждой оплате). Названия рангов задаются клубом (в сидах: Новичок, Игрок, Про, Легенда) — **собственные**, без копирования чужих.
- Скидка ранга/группы — по B.7.2. Промокоды: `bonus` (начислить бонусы), `topup_percent` (бонус к пополнению), `free_minutes`, `discount_percent` (на заказ); лимиты общие и на игрока; срок действия.
- День рождения: автоматический бонус, если игрок дал согласие; игрок вправе отказаться от маркетинга.
- Всё начисление и списание — только через ledger.

## B.13 Бронирование

- Слот-основанная модель с `tstzrange` и исключающим ограничением (нет пересечений). Минимальный/максимальный срок брони и горизонт в настройках.
- Состояния: `held` (ожидает подтверждения/залога N минут) → `confirmed` → `arrived`/`no_show`/`cancelled`/`done`.
- За 15 минут до брони ПК переходит в `RESERVED`; если игрок не пришёл за `grace` минут — бронь `no_show`, ПК освобождается, залог по правилам клуба.
- Бронь из приложения игрока и из панели; залог через ledger (`reservation_deposit`).

## B.14 Бар, склад, смены

- Заказ из оболочки создаёт `order(state=new)` → уведомление администратору → `accepted` → `delivered`; оплата с баланса игрока (или наличными на месте) создаёт запись в ledger/payments **при подтверждении выдачи**, не при заказе.
- Склад: остаток = сумма `stock_movements`; продажа вычитает; отрицательный остаток разрешён только с флагом клуба и предупреждением.
- Смена: нельзя принимать деньги вне открытой смены; закрытие смены фиксирует ожидаемую наличность и расхождение; закрытая смена неизменяема. Фискализация — через интерфейс `FiscalRegistrar` (заглушка `NoopFiscal` в MVP).

## B.15 Выпуск релизов клиента

CI собирает клиент (Linux) → `dotnet publish` → NSIS-установщик → подпись `osslsigncode` → вычисление sha256 → манифест, подписанный Ed25519 → загрузка в хранилище → запись в `client_releases` в панели по кнопке «Опубликовать». Откат — публикацией предыдущей версии как актуальной.

## B.16 Сборка, тесты, эксплуатация

`Makefile` (минимум):

```
make dev          # docker compose up (postgres, server, web dev)
make lint         # golangci-lint, eslint, dotnet format --verify-no-changes
make test         # go test ./... ; vitest ; dotnet test (Club.Core, Club.Protocol)
make e2e          # поднимает сервер + fake-client, прогоняет сценарии

```

- **fake-client** (`tools/fake-client`): эмулирует N ПК, реализует протокол, офлайн-режим, подписанный билет; на нём автоматизируются e2e-сценарии: вход, сессия, нехватка денег, потеря связи, перенос, команда блокировки, обновление.
- **CI:** lint, unit, интеграционные (testcontainers), e2e, проверка уязвимостей, сборка клиента, проверка миграций «вверх/вниз».
- **Наблюдаемость:** структурные логи, метрики Prometheus (`/metrics`: активные сессии, WS-соединения, задержка тика, ошибки), health-эндпоинты, алерты на задержку биллинг-тика > 5 с.
- **Бэкап:** `pg_dump` ежедневно + WAL при необходимости, проверка восстановления в `docs/operations.md`.
- **Миграции:** только вперёд-совместимые; никаких деструктивных миграций без шага депрекации.
